### Three API constraints found (these shape how the above was done)

1. **`PUT /campaigns/{id}` wants `emails` as an index-keyed object**, not an array —
   `{"emails": {"0": {...}}}`. An array returns 422 *"The emails.0 field must be an array."*
   The POST path (create) still takes a real array. Do not "fix" this to look like POST.

2. **Only `subject` / `from_name` / `from` / `reply_to` / `content` are accepted inside
   `emails.0`.** Any other key — including `preheader`, `name`, `plain_text`, `track_opens` —
   fails the same 422. There is no `/emails/{id}` endpoint (404 on GET/PUT/PATCH), so the
   native `preheader` field is **not writable through the API** and stays `null` on all 27.
   This is cosmetic only: MailerLite derives the real preview text from the hidden preheader
   div that `shell()` already emits, which matches the 4th return value of each content
   function. Confirmed independently by the automation-side note in `API-SURFACE.md`
   ("`data.preheader` is prohibited when `content` is supplied … MailerLite derives the
   preheader from the HTML's own hidden preheader div").

3. **Native Google Analytics / UTM is not settable via the API.** `settings.use_google_analytics`,
   `settings.google_analytics`, and flat `utm_*` keys are all accepted with **200 and then
   silently discarded** — `use_google_analytics` reads back `false` every time. UTM is
   therefore applied at the href level instead, via `add_utm()` in `ml_components.py`,
   called from both `build_emails.py` and `push_campaigns.py`. It tags only
   `https://hairsolutions.co*` URLs and deliberately skips `{$url}`, `{$unsubscribe}`,
   `{$tracking_url}`, `{$order_status_url}`, `{$last_viewed_product_url}`, `mailto:`, and
   Instagram. Handles the pre-existing query string on `/?stay=subscribed`. This is more
   durable than the dashboard toggle and survives re-pushes.

### Open risk 1 — unassigned ≠ no audience

MailerLite has no "no recipients" state for a campaign. With no group set, a campaign falls
back to `all_active_subscribers: true` and reports **`recipients_count: 1000`**. `groups: []`
and `segments: []` are both accepted with 200 and are **no-ops** — the fallback cannot be
cleared through the API.

So all 22 lifecycle drafts plus W-4 currently read as "1000 recipients" in the dashboard.
Nothing sends while they are drafts, but a single mis-click on *Send* in the UI would push an
order confirmation to all 999 prospects. Not fixable from the API; treat as a UI-discipline
item, or move the lifecycle content into automation email steps and delete these campaigns.
